# AGENTS.md — правила для агентів, що працюють у цьому репозиторії

Спершу прочитай [`docs/01_requirements.md`](docs/01_requirements.md) і [`docs/02_architecture.md`](docs/02_architecture.md). Вони визначають, що будувати. Цей файл визначає, як.

Мова документів — українська. Ідентифікатори, коментарі, докстрінги, повідомлення комітів, тексти помилок і інтерфейс вебморди — англійською.

Головний принцип: код має бути таким, щоб інший агент чи людина могли його зрозуміти, проаналізувати й змінити, не відтворюючи контекст із голови автора. Швидкість не є виправданням для халтури. **Не обрізай кути** (don't cut the corners): якщо щось зроблено наполовину, це не зроблено.

## 1. Порядок роботи

1. Нова функція чи значна зміна починається з нової гілки (`feature/<коротко>`, `fix/<коротко>`) до першої правки. Працюй у ній до кінця. Не зливай у `main` і не повертайся на `main`, поки власник репозиторію не скаже.
2. Перед кодом: прочитай існуючий код, який зачіпаєш, і зрозумій архітектуру. Склади послідовність змін, яка не ускладнить наступні кроки. Якщо нова інформація суттєво змінює план, переглянь його, а не латай.
3. Один коміт — одна логічна зміна. Повідомлення комітів англійською, у наказовому способі, пояснюють навіщо, а не лише що. Без рядків про співавторів і ідентифікаторів сесій.
4. Перед тим як сказати «готово», запусти повний набір перевірок (розділ 3) і переконайся в нульовому коді завершення. Звітуй чесно: що пройшло, що ні, що пропущено.
5. Якщо вимоги суперечать одна одній або чогось бракує, не вгадуй мовчки: зафіксуй питання, запитай власника репозиторію. Зміни вимог вноси у `docs/` тим самим комітом, що й код.

## 2. Інструменти й середовище

- Python 3.13+, менеджер пакетів `uv`. Залежності додавай через `uv add` (у `pyproject.toml` і `uv.lock`), не вручну і не через `pip`.
- Усі команди запускай через `uv run`.
- Тимчасові файли клади в `D:\tmp` (Windows), а не в `/tmp`.
- Нову залежність додавай, лише якщо її відсутність дорожче за підтримку. Для кожної пояснюй у коміті чому. Перевіряй, що вона підтримується й має типи.

## 3. Обов'язкові перевірки

Усі мають завершуватися з кодом 0, без попереджень:

```
uv run ruff check .
uv run ruff format --check .
uv run mypy
uv run pytest
```

Правила:

- **Лінтери завжди проходять і не видають помилок.** Не здавай роботу з червоними перевірками, навіть якщо «помилка не моя».
- Заборонено глушити перевірки, щоб пройти їх: `# type: ignore`, `# noqa`, `# pyright: ignore`, `cast(...)` для обходу помилки типів, `Any` на межі, розширення `ignore` у конфігурації ruff чи mypy, пропуск тестів (`skip`, `xfail`) без пов'язаної задачі. Якщо виняток справді неминучий (баг у стороннього пакета), він має бути вузьким, з коментарем-поясненням і посиланням на першоджерело проблеми, і про нього треба повідомити власника репозиторію.
- Конфігурація mypy: `strict = true`, плюс `warn_unreachable`, `disallow_any_explicit`, `enable_error_code = ["ignore-without-code", "redundant-expr", "truthy-bool"]`. Ruff: широкий набір правил (мінімум `E, F, W, I, N, UP, B, A, C4, SIM, RET, ARG, PL, PTH, TRY, RUF, S, ASYNC, PERF, ANN, T20, DTZ, ERA, FBT`), `select` розширюється, а не звужується.
- Додаючи чи змінюючи конфігурацію лінтерів, не послаблюй її без погодження.

## 4. Типізація

- Усе строго типізоване: параметри, повернення, атрибути, змінні, де тип не очевидний. Жодних неявних `Any`. Явний `Any` заборонений (`disallow_any_explicit`).
- Дані із зовнішнього світу (HTTP, БД, середовище, JSON, MCP-виклики) типізуються моделями Pydantic або `dataclass(frozen=True, slots=True)` на межі. Словники `dict[str, object]` по коду не передавати.
- Використовуй `Literal`, `Enum`, `NewType` або дискриміновані union замість «магічних» рядків і чисел. Статуси, види помилок і режими — це типи, а не рядки.
- Колекції в публічних інтерфейсах: `Sequence`, `Mapping`, `Collection` для входу; для виходу — незмінні типи (`tuple`, `frozenset`), якщо немає причини для змінних.
- Для повʼязаних даних використовуй `Protocol` для залежностей, які мають кілька реалізацій (`Fetcher`, `Extractor`, репозиторії).
- Дженерики й `TypeVar` — коли без них код дублюється. Не вигадуй абстракцій «на майбутнє».

## 5. Parse, don't validate

- На межі системи (HTTP-вхід, MCP-аргументи, конфіг, рядки з БД, відповіді зовнішніх сервісів) перетворюй сирий вхід на **тип, що неможливо створити в невалідному стані**, і далі передавай саме цей тип. Не перевіряй те саме знову в п'яти місцях.
- Приклад: функція приймає `NormalizedUrl`, а не `str` з коментарем «має бути нормалізованим». `NormalizedUrl` створюється лише парсером, який повертає помилку для невалідного вводу.
- Невалідний стан має бути непредставним: `NonEmptyStr`, `PositiveInt`, `AgentId`, `Sha256Hex` тощо. Не плодити `Optional` там, де значення за правилом завжди є; якщо два поля або є обидва, або нема жодного, моделюй це одним `Optional`-обʼєктом.
- Парсери чисті й детерміновані: без I/O, годинників і глобального стану. Вони легко тестуються таблицею вхід → вихід.
- Не використовуй `assert` для перевірки зовнішнього вводу; `assert` — лише для інваріантів, що не мають порушуватися.

## 6. Обробка помилок

- **Ніколи не ковтай помилки.** Заборонені `except: pass`, `except Exception: return None`, логування замість обробки, повернення порожнього значення як «все гаразд».
- Ловити найвужчий можливий тип виключення й лише там, де можна зробити щось осмислене: перетворити на значення, повторити, додати контекст, закрити ресурс. Інакше нехай піднімається вище.
- Очікувані збої доменної логіки (сайт повернув 403, таймаут, не вдалося витягнути текст) моделюй як **значення** (дискримінований union / `Result`-подібний тип), а не як винятки. Викликач повинен бути змушений їх обробити, mypy перевіряє вичерпність через `assert_never`.
- Неочікувані збої (баг, порушений інваріант, недоступна БД) — виняток, що піднімається до межі процесу, де його логують зі стеком і перетворюють на відповідь `error`/HTTP 500 без витоку внутрішніх деталей.
- При перепакуванні виключення використовуй `raise NewError(...) from exc`, щоб не втратити причину.
- Повідомлення про помилку містить контекст: що робилося, над чим (URL, ключ, ідентифікатор), чому не вдалося. Без секретів.
- Ресурси (клієнти, з'єднання, файли, задачі) закриваються через `async with`/`with` або `try/finally`. Фонові задачі `asyncio` тримай за посиланням, обробляй їхні винятки й скасовуй при завершенні.
- Усі мережеві й IO-виклики мають таймаут. Нескінченне очікування заборонене.

## 7. Дизайн і структура коду

- Дотримуйся шарів із `docs/02_architecture.md`: `domain` без I/O; адаптери (`mcp_api`, `web`) тонкі; залежності передаються через конструктор. Заборонені глобальні змінні зі станом і імпортні побічні ефекти.
- Функція робить одну річ. Якщо в назві треба написати «and», розділи. Орієнтир — функція, що вміщається на екран; модуль — одна відповідальність.
- Розділяй чисту логіку й I/O. Чисту логіку тестуй без моків.
- Не дублюй: якщо та сама логіка зʼявляється втретє, виділи її. Але не абстрагуй передчасно: дві подібні речі ще не причина для базового класу.
- Композиція замість наслідування; наслідування лише для `Protocol` і виключень.
- Імена повні й описові (`fetch_started_at`, а не `t0`). Без скорочень, які не є загальновживаними. Булеві змінні читаються як твердження (`is_expired`, `has_text`).
- Жодного мертвого коду, закоментованого коду, `TODO` без номера задачі чи пояснення. Невикористане видаляй.
- Не залишай «тимчасових» рішень без запису у `docs/` про те, чому й коли їх прибрати.
- Публічні функції й класи мають докстрінг з контрактом: що приймає, що повертає, які збої очікувані. Коментарі пояснюють **чому**, а не **що**.

## 8. Асинхронність

- Увесь I/O асинхронний; блокуючі виклики (CPU-важка екстракція, синхронні бібліотеки) виконуй у пулі потоків (`asyncio.to_thread`) і не блокуй event loop.
- Не використовуй `asyncio.run` усередині бібліотечного коду. Використовуй `asyncio.TaskGroup` для структурованого паралелізму.
- Скасування (`CancelledError`) не ковтати. Перед `shield` подумай, хто володіє задачею і хто її завершує.
- Спільний стан змінюй під замками або через структури, які це гарантують; описуй інваріанти в докстрінгу.

## 9. База даних

- Лише параметризовані запити, ніколи не конкатенуй SQL із вхідних даних.
- Схема змінюється тільки новими нумерованими міграціями; застосовані міграції не редагуються.
- Часові мітки — UTC, ISO 8601, з часовою зоною. Наївні `datetime` заборонені (`DTZ`). Годинник інжектується в логіку, а не береться з `datetime.now()` усередині неї, щоб тести були детермінованими.
- Транзакції короткі. Запис журналу подій не має ламати основну відповідь, але й не губитися мовчки.

## 10. Безпека

- URL від агентів — недовірений вхід. Правила SSRF з `docs/01_requirements.md` розділ 7 реалізуються в `domain` і мають повні тести (IPv4, IPv6, IPv4-mapped, редиректи, DNS rebinding, `user:pass@`, нестандартні порти).
- Збережений чужий HTML не виконується й не вставляється в сторінки без екранування. Шаблони Jinja2 з автоекрануванням завжди увімкненим.
- Секрети — лише зі змінних середовища; не логуй їх, не клади в образ, не коміть. Контейнери працюють не під root.
- Не додавай ендпоінтів, що слухають не loopback.

## 11. Тести

- Кожна нова поведінка має тест; кожна виправлена помилка — регресійний тест, що падає без виправлення. Спершу тест, що падає, потім код.
- Тестуй поведінку, а не реалізацію. Ніяких тестів, що лише повторюють код.
- Піраміда: багато швидких тестів чистої логіки (парсери, нормалізація URL, SSRF, TTL), менше інтеграційних (SQLite у тимчасовій БД, фетчер проти локального тестового HTTP-сервера, MCP-виклики через клієнт), мінімум наскрізних.
- Конкурентність (single-flight, ліміти домену, скасування) тестується детерміновано: керовані події й фейковий годинник, а не `sleep`.
- Заборонено нестабільні тести. Тест, що то падає, то проходить, — це баг, який виправляють негайно, а не перезапускають.
- Мережа в тестах — лише loopback-сервер, піднятий тестом. Реальні інтернет-запити заборонені.
- Покриття не самоціль, але гілка помилки без тесту вважається нетестованою.

## 12. Логування й спостережуваність

- Структуровані логи (JSON, поля, а не склеєні рядки), кожен запит має `request_id`, що збігається з полем у `events`.
- Рівні: `error` — потрібна дія людини; `warning` — відхилення, яке система впоратилась; `info` — ключові події життєвого циклу; `debug` — деталі. Без `print`.
- Не логуй вміст сторінок і секрети.

## 13. Документація

- Зміна поведінки чи архітектури оновлює `docs/` і `README.md` тим самим комітом.
- Рішення, що неочевидні, записуй у `docs/` (коротко: контекст, вибір, чому, що відкинули).

## 14. Чого не робити

- Не ковтати помилки, не глушити лінтери, не обходити типи.
- Не додавати функціональності поза вимогами й поза поточним етапом.
- Не робити «швидке виправлення» симптому, якщо це ускладнює майбутні зміни; шукай причину.
- Не залишати проєкт у стані, де перевірки червоні, а робота названа завершеною.
- Не вигадувати факти про сторонні бібліотеки: читай їхню документацію й вихідний код, перевіряй поведінку запуском.
- Не пропускати кроки з пункту «Порядок роботи» заради економії часу.
