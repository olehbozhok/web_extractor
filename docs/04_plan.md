# План реалізації

Дата: 2026-11-09. Вхід: `01_requirements.md`, `02_architecture.md`, `03_mcp_interface.md`, спайки `docs/spikes/`. Виконавець працює за `AGENTS.md`: кожна віха в окремій гілці від `main`, злиття в `main` лише за командою власника, перед закриттям віхи повний набір перевірок із кодом 0.

## 1. Принципи послідовності

- **Спершу фундамент без I/O, потім адаптери, потім складання.** Порядок віх повторює шари з `02_architecture.md`: `domain`, далі `storage`, `fetchers`, `extractors`, далі `service`, далі `mcp_api` і `web`. Зворотні залежності неможливі, тож пізніші віхи не змушують переписувати ранні.
- **Інтерфейси `Fetcher` і `Extractor` закладаються у віху 1**, щоб Crawl4AI (етап 3) підключався без зміни конвеєра.
- **Кожна віха закінчується працездатним станом**: перевірки зелені, документація оновлена, є тести на всі нові гілки помилок.
- **Тести першими.** Тест, що падає, потім код (розділ 11 `AGENTS.md`).
- **Жодних тимчасових обхідних рішень без запису в `docs/`.**

## 2. Віхи

Розмір: S (кілька годин), M (до двох днів), L (більше).

### Етап 1: ядро

**M0. Каркас проєкту (S).** Гілка `feature/scaffold`.
- `pyproject.toml` із `uv`, залежності й dev-залежності, `uv.lock`; пакет `src/web_extractor/`.
- Конфігурація mypy (`strict`, `disallow_any_explicit`, `warn_unreachable` та ін.) і ruff (набір правил з `AGENTS.md`, розділ 3) у `pyproject.toml`.
- pytest із `asyncio_mode = "strict"`; один тривіальний тест.
- Скрипт або `Makefile`-аналог, що запускає чотири перевірки одним викликом.
- Готово: `ruff check`, `ruff format --check`, `mypy`, `pytest` проходять на порожньому каркасі.

**M1. Доменний шар (M).** Гілка `feature/domain`. Залежить від M0.
- Типи: `NormalizedUrl`, `AgentId`, `TaskId`, `Sha256Hex`, `NonEmptyStr`, `Status`, `FetchRequest`, `FetchResult` (`Fetched` | `FetchFailure`), `ExtractResult` (`Extracted` | `ExtractionFailure`), `PageRecord`, `Event`. Створюються лише парсерами, які повертають помилку для невалідного вводу.
- Нормалізація URL: регістр хоста, видалення фрагмента, відкидання трекінгових параметрів зі списку конфігурації, IDN, відхилення облікових даних у URL.
- Правила SSRF над адресами (чисті функції): loopback, private, link-local, multicast, reserved, IPv4-mapped, NAT64, `::127.0.0.1`.
- Логіка TTL з інжектованим годинником.
- Готово: таблично-керовані тести (вхід, вихід) для всіх парсерів і правил SSRF, включно з IPv4, IPv6 і краєвими випадками.

**M2. Сховище (M).** Гілка `feature/storage`. Залежить від M1.
- Нумеровані SQL-міграції й таблиця версій, застосування при старті.
- Репозиторії `cache_pages` і `events` на `aiosqlite`, параметризовані запити, WAL.
- Запити для статистики (агрегати за період, за статусом, за доменом, за агентом, топ повторів, перцентилі).
- Готово: інтеграційні тести на тимчасовій БД; тест на конкурентні записи; тест міграцій на порожній і вже міграційній БД.

**M3. Екстрактор і HTTP-фетчер (L).** Гілка `feature/fetch-extract`. Залежить від M1.
- `TrafilaturaExtractor`: HTML у `Extracted` / `ExtractionFailure`, метадані, формати `markdown` і `text`; CPU-важка робота в `asyncio.to_thread`.
- `HttpFetcher` на httpx: резолв DNS один раз і підключення до перевіреної IP-адреси (захист від DNS rebinding), перевірка кожного редіректу, ліміт редиректів, ліміт розміру з потоковим читанням, таймаути по стадіях, `Retry-After`, браузерний User-Agent з конфігурації.
- Тести проти локального тестового HTTP-сервера, який піднімає сам тест: редіректи, заборонені цілі, великі тіла, повільні відповіді, 403/429/404.
- Готово: усі сценарії S1, S5, S8 з вимог мають тест на рівні фетчера; тест SSRF проходить для IPv4, IPv6, rebinding.

**M4. Сервісний шар (L).** Гілка `feature/service`. Залежить від M2, M3.
- Конвеєр: нормалізація, SSRF, кеш, TTL, `fresh`, single-flight, фетчер, екстрактор, збереження, подія.
- Single-flight з `asyncio.shield`; скасування очікувача не скасовує спільну задачу; правило для `fresh`.
- Ліміти: на домен (семафор і інтервал), глобальний, час очікування в черзі (`queue_ms`).
- Запис події для кожного запиту, включно з відхиленими валідацією й SSRF; не губиться при завершенні процесу.
- Готово: детерміновані тести конкурентності (керовані події, фейковий годинник, без `sleep`); сценарії S1–S5, S8; тест, що N одночасних запитів дають один виклик фетчера.

**M5. MCP-шар і складання (L).** Гілка `feature/mcp`. Залежить від M4.
- `pydantic-settings`: конфігурація, валідація при старті.
- Composition root, `/healthz`, `/readyz`, JSON-логи з `request_id`.
- MCP на `MCPServer`: `fetch_page`, `check_urls`, `find_in_page` за `03_mcp_interface.md` (формат відповіді, помилки, `agent` з параметра або заголовка).
- Перед реалізацією: короткий пробний прогін SDK 2.x на пункти «не перевірено» з розділу 10 `03_mcp_interface.md` (безстановий Streamable HTTP, `outputSchema`, анотації), результат у `docs/spikes/03_mcp_sdk.md`.
- Готово: інтеграційні тести через клієнт MCP у процесі: кожен інструмент, помилки, обрізання й продовження, нормалізований і дослівний збіг.

**M6. Контейнеризація (M).** Гілка `feature/compose`. Залежить від M5.
- `docker/core.Dockerfile` (багатоетапний, non-root), `compose.yaml` лише з ядром, том для БД, `healthcheck`, порт лише на `127.0.0.1`.
- Приклад підключення до MCP-клієнта (`.mcp.json`) у `README.md`.
- Готово: `docker compose up` на чистій машині; `/readyz` успішний; дим-тест з клієнтом MCP.

Кінець етапу 1: критерій з `01_requirements.md`, розділ 6.

### Етап 2: вебморда

**M7. Каркас вебморди й Dashboard (M).** Гілка `feature/web-dashboard`. Залежить від M2.
- Jinja2 з автоекрануванням, статика з самохостованим HTMX, без збирача фронтенду.
- Dashboard за період: запити, hit-rate, розподіл статусів, топ доменів і URL, перцентилі, частка `unknown` агентів.

**M8. Events і Agents (M).** Гілка `feature/web-events`. Залежить від M7.
- Таблиця подій із фільтрами, сортуванням, групуванням, пагінацією; розріз за агентами й задачами.

**M9. Cache (M).** Гілка `feature/web-cache`. Залежить від M7.
- Список записів, перегляд тексту й сирого HTML у `<pre>` з екрануванням, перезавантаження, видалення.
- Готово для етапу: сценарій S7; тести відповідей сервера; перевірка XSS на збереженому шкідливому HTML.

### Етап 2.5: оцінювання інтерфейсу

**M10. Оцінювання MCP (M).** Гілка `feature/tool-eval`. Залежить від M5 (бажано від M7 для аналізу журналу).
- Набір 15–25 реалістичних задач із перевірюваними відповідями, цикл агента через API, збір метрик (точність, виклики, токени, помилки, час).
- Порівняння варіантів з розділу 8 `03_mcp_interface.md`; зміни інтерфейсу за результатами.
- Результат у `docs/`; контрольний набір задач окремо.

### Етап 3: браузерний конектор

**M11. Стенд ізоляції (M).** Гілка `feature/browser-stand`. Залежить від M6.
- Відтворити стенд зі спайку 02 (`93.184.216.0/24` і `172.30.0.0/24`, редиректор, ціль, `probe`) як compose-файл для тестів, підняти в автоматичному інтеграційному тесті.

**M12. Browser-сервіс і `BrowserFetcher` (L).** Гілка `feature/browser-fetcher`. Залежить від M11.
- Сервіс Crawl4AI із закріпленим тегом у `compose.yaml`; власний `config.yml` (знижені `pool.max_pages`, `wall_clock_s`, `text_mode`), `mem_limit`, healthcheck-скрипт із самозавершенням (типізований, за `AGENTS.md`).
- `BrowserFetcher`: відображення полів `/crawl` у типи `domain` (`redirected_url`, `redirected_status_code`, евристика «anti-bot» не береться як єдина ознака блокування), `process_iframes`, `page_timeout`, ліміт одночасних браузерних запитів менший за `pool.max_pages`.
- Режим `render=auto` із переходом на браузер за порожнім результатом.
- Готово: сценарій S6; тести стенда (редіректи в приватні цілі завершуються 403 без доступу до цілі; падіння браузера дає `error` і відновлення); метрика кількості процесів Chromium в `/readyz`.

## 4. Ризики

| Ризик | Чому | Заходи |
|---|---|---|
| Зміни API Crawl4AI в новій версії | образ зовнішній | закріплений тег; повторний прогін стенда M11 при оновленні |
| Поведінка SDK 2.x відрізняється від припущень | читався лише README | пробний прогін у M5 до реалізації інструментів |
| Обрив клієнта не звільняє браузерну сторінку | спостережено в спайку 02 | ліміт одночасних запитів у ядрі, `page_timeout`, `mem_limit` |
| `structuredContent` дублює тіло в контексті клієнта | не перевірено | перевірка на реальному клієнті в M5/M10 |
| Порушення SSRF-захисту при refactoring | критична безпекова властивість | регресійні тести на всі випадки, окремий прогін у CI-скрипті |
| Хибне спрацювання евристики «anti-bot» Crawl4AI | безумовна евристика | статус за `redirected_status_code` і тілом, а не за `success` |
