# Оцінювання MCP-інтерфейсу (M10)

Дата: 2026-11-09. Мета — вимірювати, а не вгадувати (docs/03, розділ 8): точність, кількість викликів, помилки інструментів і час на контрольному наборі задач.

## Склад

| Файл | Зміст |
|---|---|
| `evals/tasks.json` | контрольний набір: 23 задачі п'яти видів з перевірюваними очікуваннями |
| `evals/pages.py` | детерміновані сторінки-фікстури (без мережі): довга сторінка з голкою на глибині, цитата з типографськими лапками, blocked/gone цілі |
| `evals/harness.py` | запуск агента над задачами, верифікація відповідей за `expected`, метрики (точність, виклики, помилки, час) |
| `evals/baseline.py` | детермінований rule-based агент: фіксована стратегія на вид задачі |
| `evals/mcp_client.py` | справжній ToolClient через MCP до збудованого застосунку (фетчер підмінений фікстурами, решта — робочий код) |
| `evals/run.py` | CLI: `uv run python -m evals.run --agent baseline` друкує звіт у stdout |

## Запуск

```bash
uv run python -m evals.run --agent baseline
```

Регресійний тест `tests/evals/test_harness.py` гонить повний корпус через baseline і падає, якщо хоча б одна задача не проходить: це охороняє сам набір від «підгінання».

## Результат baseline-прогону (2026-11-09)

- 23/23 задач (100%), середнє 6.65 викликів на задачу, 3 «очікувані» помилки інструментів (blocked/not_found у відповідях), ~0.9 с на весь корпус.
- Призначення baseline — не показникості, а валідація: інструменти, формат відповіді, курсорна пагінація (27 викликів `read_more` на довгій сторінці) і верифікація очікувань працюють як задумано. LLM-агенти починають порівняння з цієї планки.

## Порівняння варіантів (docs/03, розділ 8) і що залишилось власнику

Базовий прогін збудував інфраструктуру; самі **порівняння вимагають реальних LLM-агентів** (ключ провайдера в власника): варіанти для вимірювання —

1. дефолт `max_chars` (6000 / 12000 / 24000) — впливає на частоту `read_more`;
2. наявність `find_in_page` (дешева перевірка цитат проти читання всієї сторінки);
3. імена інструментів з префіксом і без;
4. формат шапки (ключ-значення проти JSON у тексті);
5. дублювання тіла в `structuredContent` (перевірити реального клієнта).

LLM-агент підключається протоколом `EvalAgent` (один метод `solve(task, tools)`, `tools` — чотири MCP-інструменти над `McpToolClient`). Адаптер для OpenAI-сумісного API — цикл «запит до моделі з описами інструментів → виклик інструмента → додавання результату → фінальна відповідь»; метрики збирає `run_corpus` без змін. Прогони з різними провайдерами не запускалися: у репозиторії немає ключа, а мережеві виклики в тестах заборонені (`AGENTS.md`, розділ 11) — тому це перша черга для власника після M10.

## Перший прогін з LLM (2026-11-09, DeepSeek)

Адаптер `evals/llm_agent.py` (SDK `openai` з `base_url` DeepSeek, ключ лише зі змінної `DEEPSEEK_API_KEY`, не виводиться). Запуск: `uv run python -m evals.run --agent deepseek --confirm-paid [--model ... --tasks ...]`. Тести адаптера працюють на `httpx2.MockTransport`, без мережі.

Разовий платний прогін: модель `deepseek-v4-flash`, 6 задач (по одній-дві на вид, без пагінаційних), 22 231 токен на вході й 1 728 на виході, 21 с.

| Задача | Результат | Причина відмови за звітом |
|---|---|---|
| read-extract-1 | пройдено | |
| links-check-1 | пройдено | |
| quote-verify-1 | не пройдено | немає `matches` у метаданих |
| quote-verify-3 | не пройдено | у відповіді моделі немає рядка «No match» |
| links-check-2 | не пройдено | немає `url_rows` у метаданих |
| blocked-source-1 | не пройдено | статус `ok` замість `blocked` |

**Як читати цей результат (висновків про інтерфейс він не дає):**
- Метадані верифікації брались з **останнього** виклику інструмента. Якщо модель після `find_in_page` або `check_urls` робила ще виклик, `matches` і `url_rows` затиралися. Три відмови схожі на цей артефакт адаптера. Виправлено: метадані зливаються за всіма викликами (тест `test_metadata_from_an_earlier_call_survives_a_later_one`). Повторного прогону не було.
- `quote-verify-3` перевіряє відповідь за дослівним рядком «No match» з тексту інструмента. Для моделі, яка переказує своїми словами, така перевірка занадто сувора: це проблема корпусу, а не інструмента.
- `blocked-source-1`: транскрипти не зберігались, тож причину (який саме виклик дав `ok` після помилки) не встановлено. Припущення без перевірки.
- Транскриптів не було, тому розрізнити «модель помилилась» і «інтерфейс заплутав» неможливо. **Перед наступним прогоном додати запис транскриптів у файл** (без ключа) і замінити дослівні перевірки відповіді на перевірку за метаданими.
- Корисне вже зараз: ~3,7 тис. вхідних токенів на задачу при 1–2 викликах; токени кирилиці цей набір не міряє (фікстури англійською).
