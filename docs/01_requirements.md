# Вимоги: web_extractor

Статус: затверджені вимоги, код ще не написаний. Цей файл — повний контекст для агента, який реалізує проєкт. Рішення, прийняті тут, не переглядати без явної згоди власника репозиторію.

## 1. Навіщо це потрібно

Кілька LLM-агентів працюють паралельно й постійно читають веб-сторінки (новини, офіційні сайти, документи). Зараз кожен агент відкриває сторінки самостійно через браузерне розширення або вбудований fetch-інструмент. Наслідки:

- одні й ті самі URL завантажуються багато разів різними агентами;
- у контекст агента потрапляє вся сторінка разом із меню, футером і банерами, що марнує токени;
- немає спільного кешу, немає історії того, що саме агент прочитав і коли;
- немає статистики: скільки запитів, які домени блокують, які URL повторюються, де втрачається час;
- кожне джерело поводиться по-своєму (403, JS-рендеринг, iframe), і прийоми обходу не накопичуються в одному місці.

Мета: **один спільний локальний сервіс**, який агенти викликають через MCP по HTTP. Він завантажує сторінку, витягує чистий текст, кешує результат, дедуплікує одночасні запити й веде журнал усіх дій із вебмордою для аналізу.

## 2. Межі

Входить:

- отримання сторінки (статичне через HTTP, динамічне через браузер);
- витяг основного тексту й метаданих;
- кеш із можливістю обійти його;
- журнал подій і вебморда зі статистикою та переглядом кешу;
- MCP-інтерфейс для агентів, REST-інтерфейс для вебморди.

Не входить (не робити, не пропонувати без запиту):

- пошук в інтернеті (search engine);
- LLM-підсумовування чи будь-яка семантична обробка тексту;
- автентифікація користувачів, мультитенантність, доступ ззовні хоста;
- обхід капчі, платні проксі, обхід захисту, що вимагає порушення умов сайтів;
- краулінг сайтів (переходи за посиланнями за власною ініціативою сервісу).

## 3. Користувачі та сценарії

Користувачі — LLM-агенти (через MCP) і людина-розробник (через вебморду). Мережа: лише `127.0.0.1` хоста; агенти й сервіс працюють на одній машині (Windows з Docker Desktop).

Ключові сценарії:

| # | Сценарій | Очікувана поведінка |
|---|---|---|
| S1 | Агент просить URL, якого немає в кеші | сервіс завантажує, витягує текст, зберігає, повертає |
| S2 | Агент просить URL, що є в кеші й не протермінований | повертається з кешу без запиту назовні |
| S3 | П'ять агентів одночасно просять один URL | назовні йде один запит, усі п'ятеро отримують результат |
| S4 | Агент, якому потрібна незалежна перевірка, просить URL з `fresh=true` | кеш ігнорується, завантажується заново, результат оновлює кеш |
| S5 | Сайт повертає 403/429 | агент отримує явний статус `blocked`, а не порожній текст |
| S6 | Сторінка потребує JS | за замовчуванням (`render=browser`) сторінку рендерить браузер; з `render=static` агент отримує `needs_browser`, з `render=auto` сервіс сам переходить на браузер |
| S7 | Розробник відкриває вебморду | бачить статистику за період, список запитів, вміст кешу, може перезавантажити чи видалити запис |
| S8 | Агент передає внутрішню адресу (`http://192.168.x.x`, `localhost`) | запит відхиляється (захист від SSRF) |

## 4. Функціональні вимоги

### 4.1. MCP-інтерфейс

Транспорт: streamable HTTP, ендпоінт `/mcp`. Офіційний Python SDK `mcp` (`MCPServer`). Сервіс **безстановий**: сучасна специфікація MCP не має протокольної сесії, тож відповіді залежать лише від аргументів і спільного кешу. Повний аналіз дизайну інтерфейсу, чернетки описів, формат відповіді й помилок — у `docs/03_mcp_interface.md`; нижче підсумок.

Чотири інструменти, кожен під окремий робочий процес агента:

| Інструмент | Призначення | Вхід (скорочено) |
|---|---|---|
| `fetch_page` | прочитати основний текст сторінки з метаданими, порціями з продовженням | `url`, `max_chars` (за замовч. 12000, максимум 50000), `format` (`markdown` / `text`), `fresh`, `render` (`auto` / `static` / `browser`, за замовч. `browser`), `detail` (`concise` / `detailed`), `agent`, `task` |
| `read_more` | продовжити читання за коротким курсором із попередньої відповіді (`fetch_page`, `read_more`, `find_in_page`) | `cursor` (єдиний параметр; URL, формат, розмір порції й версія тексту зашиті в курсор) |
| `find_in_page` | знайти цитату чи фрагмент і повернути лише збіги з контекстом; позначає, чи збіг дослівний, чи лише після нормалізації пробілів, лапок і тире | `url`, `query`, `ignore_case`, `context_chars`, `max_matches`, `fresh`, `render`, `agent`, `task` |
| `check_urls` | перевірити живість списку URL без тексту сторінок, один виклик замість багатьох | `urls` (до 50), `fresh` (за замовч. `true`), `render`, `agent`, `task` |

Перегляд кешу (раніше `get_cached` і `list_cached`) не виставляється в MCP: він потрібен людині й живе у вебморді та REST. Повний HTML також лише у вебморді.

Вимоги до інтерфейсу:

- відповідь має вердикт вмісту окремо від HTTP-статусу (`content: ok | thin | login_wall | challenge`); PDF із текстовим шаром витягується, непідтримувані типи дають `unsupported_type`, збій DNS дає `dns` (`03_mcp_interface.md`, 3.4);
- усі входи й виходи описуються типізованими моделями (розділ 6 у `AGENTS.md`), схеми інструментів і `outputSchema` генеруються з них, а не пишуться вручну;
- відповідь: текстовий блок із короткою шапкою `ключ: значення` і тілом, огородженим маркерами недовіреного вмісту; `structuredContent` містить лише метадані (без тіла), щоб не подвоювати контекст;
- кожен збій окрім успіху повертається з `isError: true`, текстом `ERROR <вид>: <що сталося>. <що робити>` і полем `error.kind`;
- обрізана відповідь містить короткий курсор (6 символів, випадковий ідентифікатор зі стану на сервері) і явну підказку «call read_more with this cursor»; кінець тексту позначений `END OF TEXT` без курсора; прострочений або застарілий курсор дає помилку з порадою повторити `fetch_page` (`03_mcp_interface.md`, 3.3);
- порядок і тексти інструментів у `tools/list` незмінні між запитами, у описах немає змінних даних;
- анотації всіх інструментів: `readOnlyHint: true`, `destructiveHint: false`, `idempotentHint: true`, `openWorldHint: true`.

Ідентифікація агента для журналу, за пріоритетом: параметр `agent`, заголовок `X-Agent-Id`, значення `unknown`. Параметр необов'язковий; частка `unknown` показується у вебморді як показник якості налаштування клієнтів.

### 4.2. Конвеєр

```
URL -> нормалізація -> перевірка SSRF -> пошук у кеші -> [single-flight] -> фетчер -> екстрактор -> збереження -> відповідь
```

Фетчер і екстрактор — окремі абстракції (протоколи), реалізації підключаються через конфігурацію:

- `Fetcher`: `HttpFetcher` (httpx, перший етап), `BrowserFetcher` (HTTP-клієнт до Crawl4AI в окремому контейнері, етап 3; використовує `POST /crawl`, не `/html`, бо лише `/crawl` повертає сирий HTML, кінцевий код і `redirected_url`; результат дослідження в `docs/spikes/01_crawl4ai.md`);
- `Extractor`: `TrafilaturaExtractor` (модуль у процесі ядра). Екстрактор приймає HTML, на вхід не знає, який фетчер його отримав.

`BrowserFetcher` зобов'язаний:

- брати `final_url` з `redirected_url`, а код відповіді з `redirected_status_code` (поле `status_code` Crawl4AI містить код першої відповіді ланцюжка редиректів);
- застосовувати до `final_url` і до кожного елемента ланцюжка редиректів ті самі правила SSRF, що й до вхідного URL, і відкидати результат, якщо хоч один елемент веде у заборонену адресу;
- визначати статус за `redirected_status_code`, тілом і `crawl_stats`, а не лише за `success`: евристика «anti-bot» у Crawl4AI безумовна й позначає `success=false` навіть коротку справжню відповідь (спайк 02, висновок 5); код 403/429 з тілом сайту — `blocked`; 302 з кінцевим 403 і тілом `URL blocked` — окремий вид помилки `ssrf_blocked`;
- передавати `process_iframes: true` (налаштовується), інакше вміст iframe губиться;
- вимикати кеш Crawl4AI (`cache_mode: bypass`);
- не покладатися на власну перевірку URL у Crawl4AI як на єдиний захист (розділ 7);
- до виклику Crawl4AI застосовувати до вхідного URL ті самі перевірки, що й `HttpFetcher`: список дозволених портів, резолв і правила SSRF для кожної адреси. Інакше Crawl4AI відповідає `400 URL blocked (SSRF protection)` і на приватну адресу, і на домен, що не резолвиться, а агент побачив би `browser_unavailable`. Ядро повертає `ssrf_blocked` або `dns`; якщо `400 URL blocked` все ж прийшла (DNS rebinding між перевірками), це `ssrf_blocked`, а не недоступність браузера;
- невдалу навігацію (немає коду відповіді, Crawl4AI повертає `error_message` з кодом Chromium `net::ERR_*`) повертати як `network` з цим кодом у повідомленні. Так поводяться, зокрема, PDF і інші завантаження: Chromium їх не відкриває (перевірено на 0.9.5, `net::ERR_FAILED`), їх отримує лише статичний фетчер.
- передавати `page_timeout` у кожному запиті (налаштовується) і обмежувати кількість одночасних браузерних запитів значенням меншим за `pool.max_pages` у Crawl4AI: обрив запиту ядром не звільняє браузерну сторінку, вона живе до власного завершення (спайк 02, додаток);
- тримати у власному `config.yml` Crawl4AI знижені `pool.max_pages`, `wall_clock_s` і `text_mode: true`; контейнер має `mem_limit`.

Режим за замовчуванням — `render=browser` в усіх інструментах (рішення власника 2026-11-10, див. нижче). Режим `render=auto`: спершу статичний фетчер; якщо результат порожній (витягнутий текст коротший за поріг, налаштовуваний) або сторінка явно потребує JS, ядро перепробовує браузерним фетчером. Якщо браузерного фетчера немає (етап 1), повертається статус `needs_browser`.

**Рішення: браузер за замовчуванням (2026-11-10).** Контекст: статичний запит частіше провалюється (антибот-заглушки, JS-сторінки, тимчасові 403), а кожен повтор агента коштує дорожче за повільніший рендер: окремий виклик і токени на пораду та повторну відповідь. Вибір: `render=browser` за замовчуванням у `fetch_page`, `find_in_page` і `check_urls`, без автоматичного переходу на статичний фетчер. Якщо браузер не впорався, агент отримує помилку з `retry_render` (`static` після браузерних `blocked`, `timeout`, `network`, `server_error`, `browser_unavailable`) і сам вирішує, чи повторювати. Ціна: PDF і інші завантаження потребують явного `render=static` (Chromium їх не відкриває); при падінні Crawl4AI усі запити без `render` повертають `browser_unavailable`; `check_urls` повільніший (не більше двох запитів на домен одночасно, три браузерні сторінки на сервіс). Відкинуто: «браузер, а при збої статика» (власник хоче явну помилку з порадою, а не тихий перехід) і режим за замовчуванням у конфігурації (власник обрав значення в сигнатурах інструментів).

### 4.3. Результат `fetch_page`

Обов'язкові поля:

- `status`: одне з `ok`, `blocked`, `needs_browser`, `not_found`, `timeout`, `error`;
- `http_status`: код відповіді або `null`;
- `url`, `final_url` (після редиректів);
- `fetched_at` (UTC, ISO 8601), `from_cache` (bool), `fetcher` (`http` / `browser`);
- `text` (якщо запитано), `html` (якщо запитано);
- `metadata`: заголовок, автор, мова, видавець, якщо екстрактор їх знайшов; дата публікації лише зі структурованої розмітки (JSON-LD, meta, `time[itemprop=datePublished]`) разом із джерелом (`03_mcp_interface.md`, 3.4); кожне поле може бути `null`;
- `content_sha256` сирого тіла;
- `error`: структурований об'єкт (`kind`, `message`) для статусів, що не `ok`.

Помилки не маскуються: порожній текст зі статусом `ok` — недопустимий результат. Якщо екстрактор нічого не витягнув, це `needs_browser` або `error` із поясненням.

### 4.4. Кеш

- Ключ: нормалізований URL (регістр хоста, видалення фрагмента, сортування query-параметрів за потреби, відкидання відомих трекінгових параметрів `utm_*`, `fbclid`, `gclid`; список у конфігурації).
- TTL за замовчуванням налаштовується (стартове значення 24 години); `fresh=true` обходить кеш і оновлює запис.
- Зберігається сирий HTML (для перевитягу іншим екстрактором без нового запиту) і витягнутий текст. Зберігаються також помилкові результати з коротшим TTL, щоб не бити в заблокований сайт повторно.
- Старі версії запису не видаляються миттєво: при оновленні кешу змінений вміст (інший sha256) фіксується подією `content_changed` у журналі.

### 4.5. Конкурентність і ввічливість

- **Single-flight**: одночасні запити до одного ключа кешу об'єднуються в один виклик фетчера. Усі очікувачі отримують той самий результат. Скасування одного очікувача не скасовує спільний запит.
- **Ліміт на домен**: максимум одночасних запитів і мінімальна пауза між запитами на один хост, налаштовується глобально й для окремих доменів.
- Таймаути на кожну стадію (з'єднання, читання, загальний, браузерний рендер), усі налаштовувані.
- Обмеження розміру відповіді (стартово 10 МБ); перевищення — помилка `error` з видом `too_large`, а не обрізання мовчки.
- Повага до `429` і `Retry-After`: статус `blocked`, повторний запит не раніше вказаного часу.
- Максимум редиректів налаштовується; цикл редиректів — помилка.

### 4.6. Журнал подій

Кожна дія записується в append-only таблицю `events`. Мінімум полів: `id`, `ts` (UTC), `agent` (`unknown`, якщо клієнт не передав), `task`, `mcp_session_id` (необов'язкове: сучасна специфікація MCP не має протокольної сесії, поле заповнюється лише якщо транспорт його надає), `tool`, `url`, `final_url`, `cache_hit`, `fresh`, `fetcher`, `status`, `http_status`, `duration_ms`, `bytes`, `content_sha256`, `error_kind`. Подія записується також для запитів, відхилених валідацією чи SSRF-захистом.

Записи журналу не змінюються й не видаляються (окрім явного очищення за віком, налаштовуваного, вимкненого за замовчуванням).

Для браузерного фетчера додатково фіксується ідентифікатор вкладки (page/context) і ланцюжок редиректів.

### 4.7. Вебморда

Рендеринг на сервері (Jinja2), інтерактивність через HTMX; без SPA-фреймворків і збирача фронтенду. Мова інтерфейсу — англійська. Сторінки:

1. **Dashboard**: за вибраний період — кількість запитів, hit-rate кешу, розподіл за `status` і `http_status`, топ доменів за кількістю запитів і за кількістю помилок, топ URL за повторами, перцентилі `duration_ms` (p50, p95), частка `needs_browser`.
2. **Events**: таблиця подій із фільтрами (період, агент, задача, домен, статус, `cache_hit`, `fetcher`), сортуванням за будь-якою колонкою, пагінацією, групуванням і підрахунком дій (наприклад «за агентом», «за доменом»).
3. **Cache**: список записів (URL, статус, вік, розмір), перегляд витягнутого тексту, сирого HTML (у `<pre>` з екрануванням; ніколи не виконувати збережений HTML), метаданих; кнопки «перезавантажити» і «видалити».
4. **Agents**: розріз за агентами й задачами: що саме читав кожен, скільки дублів.

Вебморда не змінює дані, окрім кнопок «перезавантажити» і «видалити» запис кешу. Вона слухає той самий loopback.

### 4.8. Адміністрування

- Конфігурація через змінні середовища й файл налаштувань, усе валідується при старті; невалідна конфігурація — аварійний вихід із зрозумілим повідомленням.
- Ендпоінти `/healthz` (процес живий) і `/readyz` (БД доступна, конектори відповідають).
- Структуровані логи (JSON) у stdout; кожен запит має `request_id`, що проходить у журнал подій.

## 5. Нефункціональні вимоги

| Область | Вимога |
|---|---|
| Одночасність | не менше 20 одночасних клієнтів MCP без деградації; повільний домен не блокує інші |
| Затримка | відповідь із кешу p95 < 50 мс (без урахування розміру тексту понад 1 МБ) |
| Надійність | падіння браузерного контейнера не зачіпає кеш і статичний фетчер; ядро відповідає `needs_browser`/`error`, а не зависає; compose перезапускає впалі сервіси (`restart: unless-stopped`); контейнер браузера має healthcheck, що реально використовує браузер, і при невдачі завершує головний процес (спайк 02, висновок 3) |
| Збереження даних | SQLite у WAL-режимі на docker volume; перезапуск контейнера не втрачає кеш і журнал |
| Безпека | лише loopback; SSRF-захист (розділ 7); збережений HTML ніколи не виконується; контейнери без root, з обмеженими правами; секрети лише зі змінних середовища |
| Відтворюваність | `docker compose up` на чистій машині піднімає все; залежності зафіксовані lock-файлом |
| Супровід | типи, лінтери й тести проходять без винятків (див. `AGENTS.md`) |

## 7. Захист від SSRF

Перед кожним запитом, **включно з кожним редиректом**:

- дозволені схеми: лише `http` і `https`;
- ім'я хоста резолвиться в IP, і запит відхиляється, якщо адреса loopback, private, link-local, multicast, reserved, unspecified або IPv4-mapped такої адреси;
- перевірка робиться на IP, до якого фактично підключаються (захист від DNS rebinding): підключатися до перевіреної адреси, а не резолвити вдруге;
- порти обмежені списком із конфігурації (стартово 80, 443, 8080, 8443);
- облікові дані в URL (`user:pass@host`) відхиляються.

Захист браузерного фетчера (перевірено в `docs/spikes/02_egress_isolation.md`):

- перевірка URL у Crawl4AI відхиляє loopback, link-local, приватні адреси, `file://` і імена, що резолвляться в такі адреси;
- Chromium спрямований на вбудований egress-проксі Crawl4AI, який резолвить DNS один раз, відкидає не-глобальні адреси й підключається до закріпленого IP; на стенді редіректи й підзапити сторінки до приватних цілей завершувалися кодом 403, а цілі не отримали жодного запиту;
- ядро додатково перевіряє `final_url` і ланцюжок редиректів кожної відповіді (розділ 4.2);
- порт Crawl4AI не публікується назовні, до нього є доступ лише з `core_net`; токен обов'язковий;
- образ Crawl4AI закріплений конкретним тегом (не `latest`), оновлення проходить через повторний прогін тестового стенда зі спайку 02.

Окрему внутрішню мережу браузера з зовнішнім проксі **не використовуємо**: перевірка URL у Crawl4AI резолвить DNS у контейнері, а в мережі без DNS блокує навіть публічні сайти (спайк 02, висновок 1).

## 10. Критерії приймання проєкту

- Усі сценарії S1–S8 мають автоматичні тести.
- `uv run ruff check`, `uv run ruff format --check`, `uv run mypy` та `uv run pytest` завершуються з кодом 0 без попереджень, що вимкнені чи придушені.
- `docker compose up` на чистій машині піднімає сервіси; `/readyz` повертає успіх.
- Вебморда показує статистику за період і дозволяє переглянути кеш.
- Документація (`README.md`, `docs/02_architecture.md`) відповідає реалізації.
